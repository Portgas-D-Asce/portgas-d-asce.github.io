实现原理

一个典型的 shared_ptr 对象内部，通常包含两个原始指针（32位系统各4字节，64位系统各8字节）：

  • 对象指针：指向你实际管理的那个 T 类型的对象。
  • 控制块指针：指向一个动态分配的“控制块”结构。控制块内部通常包含：
    • 强引用计数 (shared_count) ：记录有多少个 shared_ptr 实例指向同一个对象。
    • 弱引用计数 (weak_count) ：记录有多少个 weak_ptr 实例观察同一个控制块。
    • 删除器 (deleter) ：知道如何销毁对象。
    • 分配器 (allocator) ：内存分配器的副本（如果使用了自定义分配器）。
  shared_ptr<T> 对象
+-------------------+
|  对象指针  (T*)    |  ----->  T 对象
+-------------------+
| 控制块指针 (Ctrl*) |  -----> 控制块
+-------------------+

线程安全

shared_ptr 引用计数控制块是线程安全的。 具体来说，C++ 标准保证：

  • 多个线程可以同时对同一个 shared_ptr 对象的不同的拷贝（即各自持有的 shared_ptr 实例）进行拷贝构造、拷贝赋值、析构，而不会产生数据竞争。
  • 引用计数的增减使用的是原子操作，因此即使多个线程同时增加或减少引用计数，也不会出现计数错乱。
auto sp1 = std::make_shared<int>(42);

// 线程 A
auto sp2 = sp1;   // 拷贝：引用计数 +1

// 线程 B
auto sp3 = sp1;   // 拷贝：引用计数 +1

// 线程 A
sp2.reset();      // 析构：引用计数 -1

// 线程 B
sp3.reset();      // 析构：引用计数 -1

shared_ptr 对象本身并不是线程安全的。这里 g_config 是一个普通的 shared_ptr 变量，问题在于：

  • g_config = new_cfg 内部会先增加 new_cfg 的引用计数，再修改 g_config 内部的两个指针（对象指针 + 控制块指针），然后减少旧对象的引用计数。
  • auto cfg = g_config 会读取 g_config 内部的两个指针，并增加引用计数。
  • 这两个操作如果并发执行，读取者可能看到“撕裂”的状态：比如读到新对象指针和旧控制块指针的组合，导致未定义行为（悬垂指针、计数错乱等）。
std::shared_ptr<Config> g_config = std::make_shared<Config>();

// 线程 A（写）
void update() {
    auto new_cfg = std::make_shared<Config>();
    g_config = new_cfg;  // 直接赋值给 g_config
}

// 线程 B（读）
void read() {
    auto cfg = g_config; // 读取 g_config，拷贝构造
    cfg->do_something();
}

如何保证 shared_ptr 的线程安全：

  • C++11/14/17 通过 atomic_load/stomic_store 等非成员函数保证 shared_ptr 的线程安全
  • C++20 通过 std::atomic<std::shared_ptr> 的 load/store 等成员函数保证线程安全

atomic_load/stomic_store(C++11/14/17)

std::atomic_load 和 std::atomic_store 正是为了让同一个 shared_ptr 变量的并发读写变得线程安全而存在的。只要你对这个变量的所有访问都通过这两个函数（以及配套的 atomic_exchange、atomic_compare_exchange 等），就不会出现撕裂读或数据竞争

它们到底做了什么？

  • std::atomic_load(&global_sp) 内部会保护 global_sp 的整个读取过程，确保你拿到的要么是修改前的完整 shared_ptr，要么是修改后的完整 shared_ptr，绝不会是两个指针（对象指针+控制块指针）的混合体。
  • std::atomic_store(&global_sp, new_sp) 内部会保护 global_sp 的整个写入过程，确保在它修改内部两个指针的瞬间，没有其他线程能读到半更新的状态。 换句话说，它们把同一个 shared_ptr 变量的读写变成了原子操作。
std::shared_ptr<int> global_sp = std::make_shared<int>(0);

// 写线程
void writer() {
    auto new_sp = std::make_shared<int>(42);
    std::atomic_store(&global_sp, new_sp);  // 原子替换
}

// 读线程
void reader() {
    auto local_sp = std::atomic_load(&global_sp);  // 原子读取
    if (local_sp) {
        // 使用 local_sp，后续 global_sp 的变化不影响本线程
    }
}

此时 global_sp 的并发访问是安全的。

必须遵守的规则：一致性。 atomic_load/store 只对你显式调用它们的那一次访问负责。如果你在某处写：

auto sp = global_sp;           // 直接读取，不安全！

global_sp = new_sp;            // 直接赋值，不安全！

那还是会引入数据竞争。所有对同一个 shared_ptr 变量的并发访问都必须走原子函数，没有“自动生效”一说。

这正是 C++20 的 std::atomic<std::shared_ptr> 要解决的问题——它把原子访问强制化，防止误用。

std::atomic<std::shared_ptr>(C++20)

C++11 非成员函数：功能完备，但需要手动记住对所有变量都使用它们，容易疏忽。

C++20 atomic 特化：类型系统强制所有访问都走原子成员函数，既安全又清晰。

两者的原理和内部实现几乎一样（都是靠内部锁或无锁结构来保护 shared_ptr 的原子性），只是接口便利性不同。

只保证 shared_ptr 是线程安全的，又不能保证对象是线程安全的，这有啥意义呢？

RCU

atomic<shared_ptr> + RCU 真的是神器啊！！！

定义

RCU（Read-Copy-Update） 是一种同步机制，专门为读极多、写极少的场景设计，最早在 Linux 内核中广泛使用，现在已成为并发编程中的经典模式，它的核心哲学是：

  • 读操作（Reader）：完全无锁，零同步开销，就像没有并发存在一样。
  • 写操作（Updater）：不是原地修改数据，而是复制一份副本，在副本上修改，然后原子地替换掉旧指针。
  • 旧数据回收：写者不能立刻释放旧数据，因为它可能正被某些读者使用，必须等到所有正在运行的读者都结束对旧数据的访问后，才能安全释放。

优缺点

优点：

  • 读者完全无锁，极低延迟，几乎无同步开销。
  • 不会出现读者等写者、写者等读者的“锁护航”问题。
  • 扩展性好，读端完全并行。

缺点：

  • 写者开销大（复制整个对象），不适合写频繁的场景。
  • 内存占用高（旧对象延迟释放）。
  • 宽限期后的回收可能延迟，对于内存敏感的系统需要谨慎。
  • 实现复杂，尤其是内核态，需要处理各种 CPU 状态和抢占。

std::atomic<std::shared_ptr> 本质是保证 shared_ptr 对象的读写线程安全，通过合理的利用该点可以实现对象”特殊的“读写线程安全

  • std::atomic<std::shared_ptr<T>> 确实直接保护的是 shared_ptr 这个变量本身的并发读写，而不是 T 对象内部的字段。
  • 通过一定的使用约定（对象不可变、原子替换），你可以利用它间接实现一种“特殊的对象读写线程安全”。

使用策略

读操作：必须先获取快照，然后通过快照访问对象成员

// 正确打开方式
auto snapshot = global_sp.load();
int x = snapshot->x();
int y = snapshot->y();
// ......

// 错误打开方式，会导致对象撕裂
// load 到的是对象 obj1
int x = global_sp.load()->x();
// load 到的可能是对象 obj2
int y = global_sp.load()->y();
// ......

// 导致 x 是 obj1 的，y 是 obj2 的

写操作：必须先获取快照，然后根据快照创建副本

// 获取快照
auto snapshot = global_sp.load();
// 基于快照创建副本
auto new_ptr = std::make_shared<T>(snapshot->x() + 5, snapshot->y() + 5);
// 原子替换
global_sp.store(new_ptr);

复杂对象的并发访问 你这个总结非常到位，可以说是把并发编程中“如何原子地管理复杂对象”这个问题做了一个清晰的决策树：

  • 如果 T 本身是 trivially copyable → 直接用 std::atomic，无额外开销，真正的 lock‑free。
  • 如果 T 不是，或者对象很大、更新时需要复制 → 用 std::atomic<std::shared_ptr>，通过指针的原子切换来间接实现“整个对象的原子更新”。
  • atomic<shared_ptr> 内部并非总是 lock‑free：它通常会用一把小锁来保护 shared_ptr 的读写，因此高频单点竞争时性能可能不如直接 atomic。
