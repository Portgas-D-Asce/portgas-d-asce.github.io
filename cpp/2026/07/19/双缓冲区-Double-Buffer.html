双缓冲区（Double Buffer）

双缓冲区（Double Buffering）是一种经典的并发设计模式，核心思想是用空间换无锁读：维护两份数据副本，读者永远访问其中一份（读区），写者在另一份（写区）上修改，修改完成后通过原子操作瞬间交换两份缓冲区的角色

实现原理

两个对象实例：buffer[0] 和 buffer[1]。 一个原子索引：std::atomic read_index{0}，表示当前读者应该读取哪一个缓冲区（0 或 1）。

  • 读规则：读者读取 read_index，然后直接访问对应的缓冲区，不加锁，不拷贝（拿到的是引用或指针，但要确保在读期间写者不会覆盖它——这是设计的核心）。
  • 写规则：写者计算出“非当前读区”的索引（1 - read_index），在那个缓冲区上进行修改。修改完成后，原子地更新 read_index 为这个新索引，让后续读者看到新数据。
template <typename T>
class DoubleBuffer {
public:
    // 读者通过 ReaderView 获取只读访问
    class ReaderView {
        const T& ref_;
    public:
        explicit ReaderView(const T& ref) : ref_(ref) {}
        const T* operator->() const { return &ref_; }
        const T& operator*() const { return ref_; }
    };

    explicit DoubleBuffer(const T& initial)
        : buffers_{initial, initial}, read_index_(0) {}

    // 读操作：无锁，返回当前读区的只读视图
    ReaderView read() const {
        int idx = read_index_.load(std::memory_order_acquire);
        return ReaderView(buffers_[idx]);
    }

    // 写操作：传入一个函数对象，在非当前读区上修改
    template <typename Func>
    void write(Func&& updater) {
        int curr_read = read_index_.load(std::memory_order_acquire);
        int write_idx = 1 - curr_read;               // 选择另一个缓冲区
        T& write_buf = buffers_[write_idx];
        updater(write_buf);                          // 修改它
        read_index_.store(write_idx, std::memory_order_release); // 切换
    }

private:
    T buffers_[2];
    std::atomic<int> read_index_;
};

// 使用
struct Config { /* 大对象，非平凡 */ };
DoubleBuffer<Config> db(Config{...});

// 读者
auto view = db.read();
int x = view->some_field;   // 无锁读取

// 写者
db.write([](Config& new_cfg) {
    new_cfg.some_field = 42;  // 修改写区
});

注意：这里的 write 方法需要拷贝或赋值整个对象吗？

  • 如果 updater 是直接修改写区，则无需全量拷贝，只需在原对象上修改（但写区当前必须是“过时的”或本身就是可覆盖的）。上面的例子是原地修改 buffers_[write_idx]。
  • 但在很多实现中，写区需要在每次写之前从读区复制一份，然后再修改，因为写区可能已经被之前的写操作弄脏了，或者你希望基于最新数据更新。可以在 updater 调用前添加：buffers_[write_idx] = buffers_[curr_read]; 但这会导致一次全量拷贝。
  • 是否拷贝取决于具体需求：如果写者每次都完整覆盖对象的所有字段，可以不拷贝；如果需要基于旧值修改，则必须拷贝。

多写者

标准的双缓冲区模式中，写操作通常是单线程的（或者通过锁串行化）。 原因如下：

  • 写操作直接修改 buffers_[write_idx]，如果多个写者同时修改同一个写区，会发生数据竞争。
  • 即使你“计算出各自的写区”，但写区的确定依赖于 read_index 的当前值，而 read_index 在写操作完成前不会被更新。如果两个写者同时执行：
  • 写者 A 和 B 同时读到 curr_read = 0，都决定修改 write_idx = 1。 两者同时修改 buffer[1]，竞争。

因此，标准的双缓冲区实现要求写者之间互斥，通常加一个 std::mutex

有没有无锁的多写者双缓冲？ 理论上可以，但极其复杂，需要确保每个写者操作不同的缓冲区且索引更新不冲突，通常不值得，因为写操作本身就稀缺，加锁开销可忽略。

线程安全

场景重现：

  • 初始状态：read_index = 0，读者正在读 buffer[0]。
  • 写者第一次：计算出写区为 1，修改 buffer[1]，完成后 read_index.store(1)。
  • 此时新的读者会读 buffer[1]，但之前已经开始读的读者可能还抓着 buffer[0] 的引用。
  • 写者第二次：因为现在 read_index = 1，写者选择写区为 buffer[0]，并开始修改它。
  • 而如果那个“老读者”还握着 buffer[0] 的引用没有释放，写者和老读者就并发访问了同一个 buffer，产生数据竞争。

总结出来就是：

  • 在读者长时间持有旧缓冲区的条件下，读写竞争就会出现（三缓冲区只能缓解，不能彻底解决）
  • 使用双缓冲的前提是读者不会长时间持有旧缓冲区

为什么图形学中三缓冲能“彻底”消除撕裂？

  • 在图形渲染中，读者（显示器）以固定频率（如 60Hz）读取前缓冲（front buffer），读取是持续不断的，每 16.6ms 刷新一帧。
  • 写者（GPU）渲染速度不稳定。使用双缓冲（前+后）时，如果 GPU 渲染太快，它必须等待下一次垂直同步才能交换，否则会覆盖正在显示的缓冲导致撕裂。
  • 三缓冲引入第三个缓冲区作为额外的后缓冲，允许 GPU 在显示器读取前缓冲时，渲染到后缓冲 1，完成后立即交换到后缓冲 2，而显示器仍然读前缓冲。
  • 这样 GPU 不会因为等待显示器而闲置，并且保证被修改的缓冲区永远不会是当前正被显示器读取的那个。显示器读取的缓冲区始终是交换链中特定那个，而交换链管理确保了旧缓冲区在所有引用释放前不会被重新用作渲染目标（通常通过信号量或队列）。
  • 这是硬件和驱动配合实现的，比单纯的软件三缓冲更健壮。
